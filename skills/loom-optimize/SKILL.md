# Optimize a Loom port without breaking it

Before you start you need:
- a package that passes the golden gate (`loom-port-llm` + `loom-benchmark`);
- a baseline row in `perf_log.jsonl`;
- llama.cpp ROCm numbers on the same GGUF and workloads;
- **targets from `loom-roofline`** (`bench/roofline.json`). If the user said
  "optimize this" with no target or time, run `loom-roofline` first, announce the
  targets and the 1 h budget, then loop here under its rate controller. Don't ask
  the user to pick a number, and don't stop after the first win.

## The loop (one change at a time)

1. **Measure.** Run `perf.py` (short) and `perf.py --long` (8k/16k/32k), plus
   `c4_steady.py 4`. Work on the headline metric furthest below its
   `loom-roofline` target, measured in milliseconds per token of gap, not in
   percent.
2. **Attribute by ablation.** Hardware counters are unavailable (`loom-benchmark`
   counters are UNIMPLEMENTED on gfx1151). Instead, temporarily skip a kernel or
   launch it twice in the command program, rebuild, and measure end to end. The
   delta is that kernel's cost. Wrong outputs are fine for an ablation build; never
   ship one.
3. **Change one thing** in the generator: kernel shape, fusion, tiling or dispatch.
   Keep the old variant callable. Generators take env switches (`GEMM_SKIP_PADDING`,
   `GEMM_N_FASTEST`, `FLASH2_KT`, …) so A/B is a rebuild, not a code revert. Both
   GEMM switches are **on by default** in `gen_llm.py`; `GEMM_N_FASTEST=0` turns one
   off. Build each variant into its own package dir and serve them on different
   ports.
4. **Kernel A/B test.** `python ${CLAUDE_SKILL_DIR}/ab_kernel.py OLD/program/llm.loom
   NEW/program/llm.loom KERNEL ab.loom-test` puts the old kernel next to the new one
   as `KERNEL_old`; its docstring has a case skeleton. Launch both on identical
   inputs in a `check.case` and compare with `check.expect.close`. Include a
   **negative control**: an assertion that the output is not the initial fill,
   because two kernels that both write nothing agree. Put it in a separate case that
   is expected to fail and run `loom-test ab.loom-test --device=amdgpu
   --xfail=@ab_negative_control=EXPECT/003`; the skeleton in ab_kernel.py shows it. Use the real shapes, including edge counts
   (t=1, t=4, t=63/64, a partial last tile, mixed-sequence tiles, the full context).
   Run it with `loom-test` (see the cookbook in `loom-port-llm/reference/`).
5. **End-to-end gates, all required.** In order:
   - `compare.py` on short prompts and the 1k/2k/16k/32k goldens. Every divergence
     must be a near-tie (gap ≤ ~0.6–1.0, token in the golden top-5). A new
     divergence with a large gap is a bug even if the text "looks fine".
   - `consistency.py`: concurrent outputs must equal sequential outputs. This
     catches mixed-tile and padding bugs that single requests never hit.
   - A spot-check that a few factual prompts give the **same answer as the baseline
     build**. Compare against the baseline, not the true answer: small models get
     some facts wrong in both builds.
6. **Measure again** on the same workloads. Run `perf.py` from `bench/` with a
   label for the build (add `--reverted` if you discard it). It logs the result
   and prints the controller verdict by itself. Keep the change only if it wins on the
   target metric and doesn't regress the others by more than noise (±2–3 %; run
   twice when it's close). Commit it with the numbers in the message. Keep the work dir (cfg.json, any
   generator copies you modified, the bench/ logs) under git: run `git init` once
   in the work dir, and gitignore `pkg*/` because it is regenerated by build.py.
   When you change the starter's generators, copy `starter/` into the work dir
   first and edit the copy. Act on the verdict that `perf.py` prints:
   - CONTINUE: keep going on this path;
   - REVIEW: re-ablate, then pivot or stop. Forking from an earlier decision is an
     option;
   - BUDGET: wrap up;
   - DONE: move to the next metric.

   Record design choices, including the rejected options and their numbers, in
   `bench/decisions.jsonl`.

## Measurement pitfalls

- **Microbenchmarks lie through the 32 MB MALL.** A kernel benchmark whose weights
  or KV fit in 32 MB shows 2–5× the DRAM bandwidth. Use full-size tensors (all
  layers) or end-to-end numbers.
- **Prefix caching.** Start every timed prompt with a nonce, as `perf.py` does.
- **Lazy weight load.** The first request after startup is slow, so warm up first.
- **Stale servers.** Kill the old server and confirm the port is free before
  serving the rebuilt package.
- **Mismatched ports.** A llama-server left on :8130 skews the "ROCm" numbers.
- **Server-side vs client-side timing.** llama.cpp `timings` exclude HTTP and
  tokenization; Loom numbers from `perf.py` are client-side. That favors llama.cpp
  slightly, so report it that way.
- **Near-tie noise.** Two llama.cpp builds disagree with each other at near-ties.
  Judge correctness by gap size, not by an exact-match count.

## Catalog: what worked (Strix Halo gfx1151, measured end to end)

See `reference/optimization-catalog.md` for the details, rationale and numbers of
each. In short:

**Decode (bandwidth-bound).**
1. Multi-token matvec: one lane per 32-value group with x kept in registers, plus
   1-token and 4-token variants. Weights stream once for up to 4 sequences.
2. Q4_K scale/min folding: `d·dot(codes,x) − m·Σx`, using `vector.dotf<reassoc|contract>`.
3. Fused argmax head with no logits round trip; up to 4 spans per workgroup.
4. Split-K decode attention with adaptive splits: ≤ 64 splits of about 32 keys
   each, and idle splits exit early (or c4 regresses). Use a 16-key unroll and
   compute the V offset from the K offset.
5. F16 KV cache: halves KV bandwidth at long context.

**Prefill (compute- and attention-bound).**
1. WMMA GEMMs on f16 inputs pre-scaled per row (`row_scale_f16`), with register
   prefetch of the next K-step and an N-fastest grid order so the A tile stays in
   L2. The N-fastest order was a win on Flint and Glimmer, but on Qwen3-4B it was
   4–12 % *slower* at 8k–16k prefill. A/B it for each port.
2. Padding-free GEMMs: a tile whose row scale is 0 does no work.
3. flash2, transposed flash attention: Sᵀ = K·Qᵀ and Oᵀ += Vᵀ·Pᵀ, with K/V staged
   once per KV head for all of its query heads and no LDS softmax scratch. This
   made attention 2.2× faster.
4. Listed split-K fallback for non-uniform (mixed-sequence) tiles, over live tokens
   only.
5. Per-token RoPE + KV-store kernel (6× faster than per-head launches).
6. Fused RMSNorm + f16 row scale.
7. Large prefill chunks: `prefill_capacity` 4096 for MoE; 1024–2048 is enough for
   dense models.

**Tried and did not help (don't repeat without a new reason):**
- 64-key flash tiles;
- expert gate_up prefetch;
- larger MoE tiles;
- wide GEMM tiles (more N per workgroup);
- multi-token matvec with LDS staging of x;
- ~128 keys per split in decode attention (−4 % at short context).

## Where the remaining gap usually is

- **Prefill GEMM efficiency.** We got 25–31 TFLOP/s of ~59 peak. The next steps are
  a double-buffered LDS pipeline for B (weights) and dequantizing Q4_K straight
  into WMMA fragments.
- **Small models** (≤ 1B), for example Qwen3-0.6B: decode at 2k context ran 179
  vs 193 tok/s for llama.cpp. There, the attention and launch overhead per layer
  dominates rather than weight bandwidth. Fewer, fused launches per layer, and
  fewer splits when context is short, are the levers.
- **MoE decode** is bound by the expert gather: batch the active experts' matvecs
  per token group.

## Reporting a win

Report only numbers from the same machine, the same GGUF, the same workloads and
the same session, with llama.cpp ROCm beside them, plus the correctness gate
summary. See `loom-benchmark`. For each metric, include its target, its % of
ceiling and whether it was met. Add the result to
`loom-roofline/reference/calibration.md`.
